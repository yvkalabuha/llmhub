# llmhub — гибридный LLM-диспетчер

> TL;DR: `llmhub` — отдельная служба (Python 3.12, FastAPI, SQLite WAL): единый OpenAI-совместимый API + `tasks`/`leases`; задачи правилами уходят в локальные llama-server или на облачную GPU, которую служба арендует и всегда уничтожает. Происхождение — ADR-0138/0139 (копии в `decisions/`). Деньги и секреты — выше скорости.

## Что это
- **Control plane** (systemd на 65.109.95.35, API `10.8.0.1:8095`, только VPN): очередь, router, бюджет, автомат GPU, leases, сторож. Работает без единой живой LLM.
- **Cloud plane**: арендованная GPU с образом `llmhub-infer`; контроллер туда не выносится.
- Клиенты (VoiceBot, gameDev) подключаются по `OPENAI_BASE_URL` + клиентский ключ; задачи/leases — raw HTTP (`docs/integration.md`).
- Архитектура и модель данных: `decisions/ADR-0138-cloud-gpu-manager.md`; детали — `/var/www/projectVoiceBot/platform/docs/research/T-367-cloud-gpu-manager.md` (§6, «Ворота 2026-11-04» главнее) и `T-367-tz-v2.md` (ТЗ, read-only).

## Безопасность (жёсткие правила)
- Платные ресурсы и реальные ключи провайдеров — только с явного разрешения заказчика **на каждое действие**. Тесты — на `MockProvider`.
- Секреты не в репозитории, не в логах, не в отчётах (`.env`, `secrets/` в `.gitignore`; на сервере `/etc/llmhub/providers.env`, 600).
- У адаптеров нет `stop`, только идемпотентный `destroy`; удаление — при совпадении HMAC-метки и записи в БД.
- Локальные юниты llama-server (8090/8091/8092) не управляются и не меняются; сервер 65.109.95.35 без задачи не трогать.
- Шаблон и контейнеры деплоя вне сервера запускать только с `--network none` (иначе через VPN рабочей станции они достучатся до живых 10.8.0.1:8090–8092); в тестах — `tests/conftest.py` блокирует 10.8.0.0/24 и 65.109.95.35.
- Remote — GitHub `yvkalabuha/llmhub` (main); push делает только координатор после приёмки задачи. Нет импортов из voicebot/projectVoiceBot.

## Процесс
- Работа = задача `T-XXX` в `tasks/active/` (шаблон — любой файл там), статусы todo → planned → in-progress → review → done/blocked; статус в файле и в `BOARD.md`. ID выдаёт координатор (сквозной счётчик с projectVoiceBot).
- Конвейер impl: analyst → implementer → reviewer (ADR-0013). Ворота critic + advocate (ADR-0139): ADR до принятия, план P1, вывод исследования; находка high — исправить или принять у заказчика.
- Тесты: после задачи — только тесты задачи (`uv run pytest tests/<файлы>`); полный прогон — перед релизом. Всегда `uv run ruff check` и `uv run pyright`.
- Документация — по-русски, каждый файл начинается с `> TL;DR`; код, идентификаторы, коммиты — по-английски. ADR принятый не менять — писать новый, старый `Superseded`.

## Итерации качества (ТЗ §18)
Цикл: небольшая функция → тесты → ревью (логика, гонки, перезапуски, граничные случаи, не только happy path) → исправление → повторная проверка.
- **Остановка**: тесты задачи зелёные, ruff и pyright чисто; каждый переход автомата и строка таблицы §6.3 покрыты тестом; у ревьюера нет открытых blocker/major.
- **Лимит**: ≤ 3 раундов ревью на задачу, затем список нерешённого заказчику. Сложные части (автомат + leases, бюджет, create/reconcile) — 2 независимых цикла ревью (логика/гонки; сбои/перезапуски).
- Найденные проблемы фиксируются в журнале задачи.
