# ADR-0138: гибридный LLM-диспетчер `llmhub` — локальный control plane и облачные GPU по требованию

> TL;DR: Служба `llmhub` (отдельный репозиторий `/var/www/llmhub`, systemd на сервере 65.109.95.35) даёт клиентам единый OpenAI-совместимый API плюс `tasks`/`leases`. Задачи правилами уходят в локальные llama-server (без изменений) или на облачную 3090, которую служба арендует через провайдер-независимые адаптеры и уничтожает после работы. Веса — цепочка источников (наш сервер → HF), бюджет $50/мес; при λ = 6 запр./ч пакеты `low` и быстрый старт обязательны. Accepted после ворот critic + advocate 2026-11-04.

> Перенесено из projectVoiceBot 2026-11-04: эта копия авторитетна; исходник `/var/www/projectVoiceBot/platform/decisions/` — только происхождение. Ссылки на `platform/docs/research/T-367-*.md` ведут в projectVoiceBot.

Статус: Accepted · Дата: 2026-11-04 (редакции 1–3 — 2026-11-03, Proposed; финальная — по воротам 2026-11-04)

## Контекст
- ТЗ v2 (`platform/docs/research/T-367-tz-v2.md`, ответы заказчика раундов 1–3 — обязательны): постоянный сервер (Ryzen 5 3600, 64 ГБ, без GPU) держит control plane, облачные GPU — по требованию. Главное — минимальная совокупная стоимость; локальные модели работают без облака, контроллер — без LLM; решением пользуются несколько проектов (VoiceBot, gameDev на C#/.NET).
- Исследование: `T-367-cloud-gpu-manager.md` (сводка, архитектура §6, раунд 3, «Ворота 2026-11-04»), `T-367-providers.md`, `T-367-gpu-engines.md`, `T-367-economics-router.md`.
- **Замер RunPod Community 2026-11-04 [И]**: 3090, Qwen3.8-27B UD-Q4_K_M + MTP, 64k: генерация ~78 ток/с, prefill ~1 200 ток/с, ответ 8000 ток ≈ 1,8 мин ≈ $0,007. Холодный старт от готового пода ≈ 9 мин: llama.cpp 67 с + веса с HF 457 с (~37 МБ/с) + загрузка 6 с. Расход определяют старты и простой, а не токены.
- **Экономика на замерах** (`tools/bench/T-367-sim/results-r3-measured.md`; λ = 2/4/6 запр./ч, 10 ч/сут, 30 дн, вход 6000 / выход 8000 ток), $/мес:

| Старт | idle 5 мин | пакет 5/30 + drain |
|---|---|---|
| 9 мин (HF, замер) | 26 / 38 / **46** | 12,5 / 18,6 / 23,2 |
| 4 мин (наш сервер, оценка) | 20 / 32 / 40 | 8 / 13 / 18 |
| 2,5 мин (образ + кэш, оценка) | 18 / 30 / 38 | 7 / 11,5 / 16 |

  При λ = 6 и старте 9 мин idle 5 стоит $46 > `budget_month` $45.
- Остановленный ресурс у всех провайдеров либо платит за диск, либо stop нет. Лимит трат RunPod пользователь не задаёт (платформенный $80/ч).

## Варианты
| Вариант | За | Против |
|---|---|---|
| A. RunPod Serverless | нет своего жизненного цикла | 24 ГБ $0,75/ч; холодный старт 32B 90–324 с; привязка |
| B. Прямые вызовы провайдера из агентов | просто | привязка; нет общего учёта, очереди и сторожа; утечки |
| C. Постоянный инстанс (stop/start) | быстрый старт | диск в stop платный, GPU может не вернуться |
| D. Always-on GPU | нет ожидания | ~$66/мес только на окно 10 ч |
| E. **Свой диспетчер: правила + очередь + leases + адаптеры + только destroy + независимый сторож** | без привязки, контроль денег, локальный запасной путь | больше кода; холодный старт на сеанс |
| F. dstack как оркестратор вместо своего адаптера | готовые fleets/idle, меньше кода адаптера | своё понятие жизненного цикла; утечки и время старта не проверены — spike этапа 4 |

## Решение
Вариант E; F проверяется как реализация адаптера (п. 3). Детали — `T-367-cloud-gpu-manager.md` §6 и «Ворота 2026-11-04».
1. **Два уровня и место.**
   - `llmhub` — отдельный репозиторий `/var/www/llmhub` (свой `pyproject`, `src/llmhub`, `tests/`, `docs/`, `deploy/`; без импортов VoiceBot). Работает systemd-службой на 65.109.95.35 рядом с llama-server, API на `10.8.0.1:8095` (только VPN); локальные llama-server — через `127.0.0.1`. projectVoiceBot и gameDev — клиенты. Контроллер на облачной GPU невозможен (некому запустить, ключ на чужом хосте).
   - Cloud plane: свой образ `llmhub-infer` (llama.cpp `server-cuda` собран внутрь — без скачивания 67 с, TLS-прокси, загрузчик весов). Веса в образ не запекаются, пока не измерен кэш слоёв на хостах.
   - Контроллер не загружает моделей и работает без единой живой LLM.
2. **Локальные llama-server** 8090/8091/8092 не меняются; для `local_inference` это HTTP-клиенты с CPU-семафором (concurrency 1). 8090 используют и напрямую (мимо `llmhub`), поэтому ETA считается по реальной задержке: EWMA своих вызовов + периодическая проба здоровья/занятости.
3. **Адаптеры**: `ProviderAdapter` (`list_offers`, `create(spec, label)`, `get`, `list_owned`, идемпотентный `destroy`, `balance`, `billing_since`, `normalize_error`) + `Capability`. Метода stop нет. Порядок: Mock → (этап 4) spike dstack ≤ 1 дня → `DstackAdapter` или `RunpodAdapter` → Vast. Интерфейс от выбора не меняется.
4. **WeightSource**: упорядоченная цепочка в конфиге — `self_hosted` (наш сервер) → `hf`; R2 — опция. sha256 из манифеста, докачка Range, переход к следующему источнику при ошибке **и** при низкой скорости (< `min_speed_mb_s` после 30 с). `self_hosted` — отдельный read-only HTTPS-endpoint только для весов (порт открывает заказчик): короткоживущий одноразовый токен на инстанс, лимит скорости и одновременных загрузок; VPN и локальные llama-server не затрагиваются. Сервер — точка отказа для быстрых стартов, запасной путь — HF.
5. **Автомат на пул**: STOPPED → PROVISIONING → BOOTING → LOADING_MODEL → READY ⇄ BUSY ⇄ IDLE → STOPPING → STOPPED; ERROR → STOPPING. Таймауты состояний, `max_lifetime` 3 ч, READY = `/health` 200 + тест-запрос, решение IDLE → STOPPING — в одной транзакции с проверкой очереди и leases.
   - Инстанс после принятого destroy переходит в `PENDING_DELETE`, без подтверждения нуля за 15 мин — в `LEAKED` (инцидент, блок провайдера). Частичный UNIQUE(pool) исключает STOPPED, PENDING_DELETE и LEAKED: пул может начать новый цикл, пока старый ресурс удаляется. Бюджет и сторож учитывают такие ресурсы до подтверждённого нуля. Режим контроллера HALTED.
6. **Leases** (неявные — на задачу, явные — с пульсом, TTL 10 мин) — единственный сигнал «GPU нужна». `idle_timeout` 0–15 мин, по умолчанию 5 (заказчик). Drain после пачки, hold ≤ 8 ч, prewarm.
7. **Очередь**: SQLite WAL, urgent/normal/low; `urgent` не ждёт пакета. **Пакеты `low` (5 задач / 30 мин, ждать ≤ 90 мин) — обязательны по умолчанию**, как и быстрый старт (п. 4, образ): без них λ = 6 выходит за $45. Внутри приоритета — round-robin по клиентам.
8. **Model Router**: только детерминированные правила (ECONOMY / BALANCED по умолчанию / QUALITY); модели — псевдонимы в конфиге; облако недоступно → локальная модель с пометкой. **`data_class` клиента по умолчанию `private`** (только локально); облако — явный opt-in клиента в конфиге. Детектор секретов → локально. LLM-советник в v1 нет (этап 5).
9. **Бюджет**: оценка до запуска `P·(T_cold_p90 + Σ T_work(max_tokens) + T_idle)` + трафик; `T_cold` и скорости — по EWMA факта. Сторож $50, менеджер $45/мес, $3/сут, $1/сеанс, $0,25/задание, подбюджет `exception` $10; предупреждения 50/80/95 % и по темпу; ступени 80 % → ECONOMY для normal/low, 95 % → облако только `urgent`, 100 % → запусков нет. Нехватка средств — блокировка провайдера без повторов, без автопополнения, возобновление вручную. Общий простой/hold/prewarm распределяется по клиентам пропорционально работе их задач в сеансе (hold/prewarm — держателю lease).
10. **API**: `/v1/chat/completions` (+ `stream`), `/v1/models`, `/v1/tasks`, `/v1/leases`, `/admin/*`, `/healthz`, `/metrics`; ошибки — объект OpenAI `error` с `code`, `reason`, `retryable`, `retry_after_s`; шесть причин недоступности облака; обрезка — `X-LLMHub-Truncated`.
    - Синхронное ожидание по умолчанию ≤ 8 мин (`X-LLMHub-Wait`), затем `503` + `Retry-After` + `task_id`; таймаут клиента должен быть больше (openai-python — 600 с), долгим задачам — `/v1/tasks`.
    - **Нормативный контракт — OpenAPI и примеры raw HTTP/curl** для tasks и leases (клиент gameDev на C#/.NET). Python SDK — необязателен.
11. **Надёжность**:
    - `Idempotency-Key` хранится 7 суток; без него неявная дедупликация `sha256(client+тело)` — только пока задача в очереди/работе и ~15 мин после; 409 при конфликте;
    - конечные повторы, автомат размыкания, чёрный список хостов; create без слепого повтора (сверка по label);
    - пульс воркера и возврат зависших задач; восстановление сверкой с `list_owned`; `integrity_check`.
12. **Безопасность и владение**:
    - метка `llmhub-<op_id>-<hmac8>`; удаление только при совпадении HMAC и записи в БД; ключи провайдеров — `/etc/llmhub/providers.env` (600); ключи клиентов — хеш, отдельный админ-ключ, только VPN;
    - TLS к инстансу: режим `direct` — в фильтре офферов публичный IP/TCP-порт, сертификат на инстанс и pin отпечатка; режим `proxy` (прокси RunPod завершает TLS) — ключ API на инстанс, без pin. Какой режим доступен — проверка этапа 4;
    - баланс RunPod ≤ $25, Low balance alert включён, auto-pay выключен.
13. **Развёртывание по умолчанию**: RunPod Community 1×3090, Qwen3.8-27B **UD-Q4_K_M** + MTP (замер), `-c 65536`, q8 KV, `-np 1`; профиль `quality` — Q5_K_M (≤ 24k); альтернатива — пул 35B-A3B; 5090 — пул `exception` (потолок $0,70/ч); 70B и 2×3090 — этап 5.
14. **Объём MVP (этапы 3a–3d, Mock)**: мультиарендность урезана до ключа, `allowed_models` и `max_priority`; бюджеты и квоты клиентов, советник, R2, Vast, SDK — этап 5. Процесс — ADR-0013 + ворота ADR-0139; не больше 3 раундов ревью на задачу. Реальный провайдер — только с разрешения заказчика (D10).

## Последствия / риски
- Каждый сеанс платит холодный старт; при старте 9 мин холодный ответ ≈ 10,8 мин > синхронного ожидания 8 мин — такие запросы получают `task_id`. Цель этапа 4 — старт ≤ 4–5 мин (наш сервер + образ).
- λ = 6 при старте 9 мин превышает $45 без пакетов; с пакетами `low` и старте 4 мин запас есть. Ступени 80/95/100 % ограничивают перерасход.
- Сервер 65.109.95.35: исходящий трафик весов ≈ 17 ГБ × 450–720 стартов ≈ 8–12 ТБ/мес — проверить тариф Hetzner; скорость Hetzner→RunPod не измерена (этап 4).
- RunPod: `name` пода не уникален, теги не подтверждены — владение держится на HMAC в имени + записи в БД; дубли при неизвестном исходе create удаляются сверкой.
- Худший случай — сервер умер при живом поде: под работает до нуля баланса (≈ 90 ч при $19,85). Меры: баланс ≤ $25, Low balance alert, без auto-pay; дополнительно — самоуничтожение в поде по `max_lifetime`, если у RunPod есть ключ с правами только на этот под.
- Сторож использует код адаптеров — общая ошибка возможна; снижают отдельный процесс и сверка с биллингом провайдера.

## Проверка
- Этап 3 (Mock): все сценарии §6.3 и ТЗ §15 — отдельными тестами (10 запросов → 1 create; задача в STOPPING; новый цикл при PENDING_DELETE без второго живого инстанса в индексе; перезапуск в PROVISIONING/BUSY; бюджет и баланс без повторов; lease держит GPU 20 мин; kill → 0 ресурсов ≤ 60 с; переход WeightSource по ошибке и по скорости). Сценарии S1–S6 и RF2–RF6 через Mock совпадают с симулятором ±5 %. OpenAPI и curl-примеры проходят контрактный тест.
- Этап 4 (с разрешения, ≤ $5): spike dstack ≤ 1 дня (0 утечек, время старта) → выбор адаптера; 0 утечек; READY ≤ 10 мин в 80 % стартов, с `self_hosted` — медиана ≤ 5 мин; замер Hetzner→RunPod; режим TLS; прогноз ±30 %; ledger и биллинг расходятся ≤ max($0,05; 5 %). Если цифры меняют выбор модели/GPU — новый ADR.

## Ворота 2026-11-04: critic + advocate
Перед принятием (ADR-0139) внесено: экономика на замерах (9/4/2,5 мин) и обязательность пакетов `low` и быстрого старта; WeightSource (наш сервер → HF, токены, лимиты, переход по скорости) и образ `llmhub-infer` с llama.cpp; PENDING_DELETE/LEAKED вне уникального индекса; неявная дедупликация ~15 мин, ключ 7 суток; синхронное ожидание ≤ 8 мин; режимы TLS `direct`/`proxy`; `data_class` по умолчанию `private`; EWMA для 8090; распределение общего простоя и round-robin, урезанная мультиарендность MVP; советник убран из v1; OpenAPI + curl нормативны; отдельный репозиторий `/var/www/llmhub`, квант UD-Q4_K_M; spike dstack перед адаптером; риски RunPod `name` и смерти сервера.
