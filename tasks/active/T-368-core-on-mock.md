**Находки** (воспроизведения в `tests/test_review2_failures.py`)
- **major F-R2-4: сторож не работает при испорченной БД, KILL не исполняется.** `reaper/__main__.py:369-370` открывает БД через `connect`+`migrate`, без `integrity_check` и без режима работы без БД. На испорченном `state.db` процесс падает (`sqlite3.DatabaseError`) раньше, чем доходит до KILL-файла. При мёртвом контроллере ресурсы с нашим HMAC никто не уничтожает. Второй эффект: если контроллер поместил файл в карантин (`open_state_db` → `_quarantine`), уже запущенный сторож продолжает писать в переименованный inode. Он не видит `safe_mode=1`, а его инциденты попадают в карантинный файл. Тест: `test_reaper_process_kill_file_with_corrupt_db` (slow). Исправление:
  - в `Reaper.run_loop` и `_main` ловить `sqlite3.DatabaseError`. При этой ошибке включать аварийный режим: если есть KILL-файл, вызвать `destroy` для каждого ресурса из `list_owned` с верным HMAC (часть `kill_pass` без БД), писать в stderr и повторять каждый проход;
  - на каждом проходе открывать соединение заново или сравнивать `os.stat(state.db).st_ino` с inode открытого файла и при расхождении переподключаться.
- **major F-R2-3b: строка пула, удалённого из конфига, роняет `Controller.start()`.** Состояние READY → `recovery._reconcile_row` → `machine.settle_idle` → `idle_stop_reason` → `cfg.pools[pool]` даёт KeyError (`machine.py:248`). Так происходит на каждом `step()`: контроллер не стартует, и вместе с ним останавливаются KILL-файл, teardown и все пулы. Тот же класс ошибки: `controller.py:270`, `self.adapters[row["provider"]]` (провайдер выключен, а строка жива). Тест: `test_restart_with_pool_removed_ready_instance_does_not_crash`.
- **medium F-R2-3a: строки удалённого пула контроллер не разбирает никогда.** Teardown и решение о простое выполняются в `_step_pool` только для `cfg.pools` (`controller.py:395-417`).
